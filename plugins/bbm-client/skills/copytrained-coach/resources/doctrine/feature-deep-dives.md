# Feature Deep Dives — Doctrine

## Principles (rules)

### Purpose and placement
- After the high-level How it Works, deep dive on each key feature (coaching, community, toolkits, and so on). For apps and software, demonstrate how each feature works in more detail. This is a must-have section.
- Place it after How it Works, or after What You'll Learn. There is no hard rule; try both and see what flows.

### What each deep dive covers
- A unique, compelling name for the feature.
- A benefit or promise-driven headline, rather than just the feature name.
- What it is and how it works.
- The unique mechanisms, frameworks, or technology inside it, where you have them (naming them adds curiosity and differentiation).
- The "so what?": the problem it solves, the result it delivers, or an objection it handles.
- A visual hook (image, screenshot, gif, or video).

### Framing and perceived value
- Frame the value well. Name the collection (a "Support System," an "arsenal of unfair advantages") rather than just listing features. Acknowledge bad past experiences and explain why yours is different. Position core features as core, not as "extras." Tie each feature to the reader's real desires and fears.
- Keep it believable. Powerful, high-value framing works only if the product delivers on it. If you cannot deliver on a big promise, tone it down. Do not overpromise or over-inflate.

## Examples

- **Deep dives with visuals and objections (Product Flywheel Framework):** the Training deep dive (a flywheel visual, plus objections handled, "without moving so fast you break things"); the Toolkits (a long list of done-for-you assets mapped to real challenges and desires); the Coaching System (a Slack screenshot showing it in action, then the objection "how much support will I actually get?"). — why it works: each deep dive explains what it is and how it works, with a visual hook and an objection addressed.

- **Naming the collection, tying to desires and fears (Employee to Entrepreneur):** "meet your Support System," then email coaching, the coaching vault, and lifetime updates, each with what it is, how it works, a benefit, an objection, and a value, framed as "the reason our students get results, not an extra." — why it works: it names the collection, positions core features as core, ties them to desires and fears, and lifts perceived value while still delivering on the promise.

- **Mini deep dives for a low-ticket product (Look Legit, $49):** benefit headlines ("How to spark major authority"), reasons to care ("your homepage is up to 50% of total pageviews"), and named frameworks ("the 6 key elements," "the 5-step social proof formula"). — why it works: even a low-ticket product benefits from mini deep dives with benefit headlines, reasons-to-care stats, and named frameworks.

- **Named frameworks that spark curiosity (Part-Time YouTuber Academy):** the HIVES Framework, the Infinite Content Engine, the Idea Generation Machine, each tied to saving time and avoiding wasted effort. — why it works: catchy named frameworks differentiate the product and spark curiosity, and each is tied to the audience's core desire (stop wasting time on things that don't work).

## Scoring criteria

1. **Has a deep dive for each core feature:** Is there a Feature Deep Dives section with a deep dive for each core feature? MET when each key feature gets a real deep dive. PARTIAL when some features are covered and others skipped. MISSING when there are no real deep dives.
2. **Each feature is named and framed by its benefit:** Does each deep dive carry a distinctive name and a headline that leads with what it does for the reader rather than what it is? MET when both hold throughout. PARTIAL when the names are there but the headlines are descriptive labels. MISSING when features arrive as bare nouns.
4. **Each feature explains what it is, how it works, and the so-what:** Does the dive go past description into why the reader should care? MET when all three land per feature. PARTIAL when the mechanics are covered and the so-what is implied rather than said. MISSING when it reads as a specification.
5. **Names the unique mechanisms or frameworks inside each feature:** Does it name the unique mechanisms, frameworks, or technology inside the features? MET when named mechanisms appear where they exist. PARTIAL when a mechanism is implied but not named. (product-dependent — set aside where a feature genuinely has no named mechanism; never invent one.)
7. **Frames the value well and believably:** (violation check) Does it frame the value well (tying features to real desires and fears, positioning core features as core) without overpromising or over-inflating? MET when the framing is strong and believable. PARTIAL when it is flat, or edges into overpromising. MISSING when it over-inflates in a way the product could not deliver, or lists features with no framing at all.
8. **Includes a visual hook for each feature:** Does each feature have a visual hook (image, screenshot, gif, or video)? (visual — audit must ask the user)
