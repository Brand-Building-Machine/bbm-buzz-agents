Purpose: give a fast, whole-page read of a sales page. It maps the copy to the key sections, says which are present, missing, strong, moderate, or weak, explains why in plain language, suggests which missing sections to add and where, gives specific section-by-section improvements, and ends with a prioritized to-do list. It is a page-level overview, not a deep single-section audit.

Invoke: "run the Section Map audit" / "run light page audit" (or "light-audit this page"), then I'll paste the copy or give the link.

This skill ASSESSES and SUGGESTS. It may show short directional examples of a fix ("turn X into something like Y"), using placeholders for any real facts. It does NOT write or rewrite the finished copy on its own; rewrites follow `rewrite.md` when asked, and are offered only in SKILL.md's close. If the user wants the full, precise "Meets X of Y" score on one section, run the deep `resources/section-audit.md` on that section.

## Any copy, not only sales pages

- **Where this file says "page", read "the piece being audited".**
- **Identify the piece first**, per SKILL.md's run and `copy-types.md`'s "How to use this file", before anything is judged.
- **Scope.** A sales page uses `section-set.md`, as below. Any other type uses its `copy-types.md` entry's parts, mapped to the doctrine files the entry names, and its stages replace The Opening / The Body / The Offer / The Close wherever this file groups sections.
- **Every handling note in this file that names a sales-page section applies wherever a part maps to that section's doctrine.** On other types, the entry's watch-outs apply alongside it.
- **The score** follows `audit.md`'s type layer.
- **★ Depth follows length.** The report is as long as the piece needs. A whole-page cross-check that does not fit the piece (flow, transitions or pacing on a three-line ad) is not run, silently.
- **★ Judge the piece by its own kind**, never by how far it is from the examples the doctrine learned from (`copy-types.md`, rule 3).
- **Urgency is never judged as genuine** (`audit.md`, S2).

## Scope (the whole page)

**The audited section set lives in `resources/section-set.md`. Read it; this file carries no copy of it.**

**Map the copy to those sections by FUNCTION, not by looking for labels.** Not every page has every section, so judge relevance per step 4 and the section-specific handling notes below.

**Proof and flow get a LIGHT whole-page read here; the deep versions live in their own skills.** This light audit includes a quick proof scan and a quick flow scan (the two subsections after the handling notes). It does not replace the deep skills: the section-by-section flow and craft audits are `resources/deep-audit.md` (with `resources/doctrine/flow.md`). Keep both reads light, and point the user to the deep skills when they want more.

## Section-specific handling (apply during relevance judgment in step 4 and scoring)

These override the default logic for a few second-part sections:

- **Guarantee.** If a guarantee exists, improving it is a NICE-to-have. If NO guarantee is mentioned anywhere on the page, adding one is a MUST (count its absence as a real gap).
- **Buy buttons.** When banding, also check for payment plans: is a plan offered where the price warrants one, and is it framed as a saving. Note it if a plan is absent and would fit.
- **Price justification.** Optional. If present, band it. If absent, you may suggest it, but ALWAYS as optional (some sellers deliberately leave it out); never a must, and its absence does not count as a scored gap (set it aside).
- **Product tiers.** If tiers exist, band how well the copy around them is written (each tier named, what and how, benefits, who it's for, any tier-specific proof). If there are none and the product plausibly could have them, suggest them as a NICE-to-have (not a scored gap). For a genuinely single-tier product, set aside.
- **Client journey.** An optional graphic (a visual of the path from A to B). Only scan and band it IF one exists. Never suggest adding one, and never count its absence as a gap (set it aside silently, do not list it as missing).
- **Guided tour.** Scan and band if present. If absent and it clearly fits (software, an app, a platform, or a membership where showing the inside would help), you may suggest it as a NICE-to-have. You cannot judge the video itself in a light audit, so assess only that the section exists and is set up well (its framing and what it promises to show); say plainly that the video's quality is out of scope here.
- **Sample lesson.** Scan and band if present. If absent, suggest adding one (a free taste of the teaching) as a NICE-to-have. Its absence is not a scored gap.
- **Urgency and scarcity.** Focus on the NATURAL urgency the page already has and how well it is communicated (a real deadline, limited seats, a cohort start, a price about to rise, or the cost of waiting). Do NOT suggest adding urgency as an improvement. The one exception: if the page is clearly time-gated or slot-gated (a real deadline or limited spots), check whether that urgency reads clearly and prominently, and flag it if it is buried, vague, or easy to miss.

**Scoring the optional sections:** when an optional-when-absent section (client journey, guided tour, sample lesson, price justification, or product tiers on a product that could have them) is NOT on the page, set it aside from the score rather than counting it as a zero gap. Still surface guided tour, sample lesson, price justification, and product tiers under "sections worth adding" as NICE or OPTIONAL (never MUST). Only near-universal-and-missing sections (offer introduction, buy buttons, FAQ, close, and a guarantee when none exists) count as scored gaps.

**Craft layer:** read `resources/lean-editing.md` and apply it as a light lens (see step 2). Deeper craft has its own skill (`resources/deep-audit.md`) for when the user wants that depth.

## The light proof check (a quick whole-page scan, not a full proof audit)

Alongside the section work, do a quick proof scan from the copy alone. Do NOT ask the user; go by what the page shows, its copy and its images, and name anything unread in the "couldn't read" line. For background on the proof elements, see `resources/proof-elements.md`. Check three things:

1. **Enough proof across the page?** Scan for proof of any kind: written testimonials, video testimonials, screenshots, case studies, before/afters, results with real numbers, named clients or logos, studies or metrics, star ratings. Form a rough sense of whether there is enough to make the page's claims believable, or whether the page is thin on proof. (Here just gauge overall presence.)
2. **Proof positioned in the right places?** The pattern that works: a little proof early to build trust up front, with the bulk of the testimonials landing in the second part, some way after the product introduction (where the reader is deciding to buy). Flag the two common misses: no proof at all until the very bottom (so the early claims go unbacked and the reader doubts them), or all the proof crammed at the top with none near the offer.
3. **Bold claims backed on the spot?** Notice any claim that leans hard to believe (a big number, an outsized promise, a line that reads as too good to be true) that is not immediately followed by a piece of proof. This is the light version of proof placement: flag only the obvious cases, where a doubtful reader is most likely to drop off, and say to back that claim right there.

Report this as a short "Proof across the page" read. Never fabricate proof; where it is missing or misplaced, the fix is to add or move real proof.

## The light flow check (a quick whole-page scan, not a section-by-section flow audit)

Also read the page start to finish once for flow, at a high level only. This is NOT the deep flow audit (that lives in `resources/deep-audit.md` and `resources/doctrine/flow.md`, run on request). Here, just notice any OBVIOUS breaks:
- a tangent that pulls the reader off the core idea,
- an abrupt jump between sections with no bridge (watch the opening, and the move into the offer),
- a spot where the order feels off, or the reader would get confused or start skimming.

If the page reads smoothly, say so in a line. If there are obvious breaks, name the two or three worst by where they sit (for example, "the jump from the opening story straight into pricing is abrupt") and give the quick fix in a few words (add a bridging line, move a section, cut a tangent). Do not produce a section-by-section map or a flow score here; keep it to the obvious problems only.

## Steps

1. **Load the doctrine.** Read the doctrine files for the sections in the scope tables above (their Scoring criteria + Principles), plus `resources/lean-editing.md` and `resources/coach-voice.md`. Follow the coach-voice file for the wording of everything you write, and apply its never-say rules to your OWN prose before sending. If the pasted copy is clearly only the first part of a page, you can skip loading the second-part doctrines, and vice versa.
2. **Apply the craft lens lightly.** Use the 8 lean-editing checks (voice, authenticity, consistent first person, plain language, the audience's real words, concrete and vivid, genuine emotion, tight) as a lens that INFORMS each section's band and shows up in the improvements. Do not score the 8 craft items one by one here (that's the deep audit's job). If a section is structurally complete but has weak voice, vague language, or no real emotion, that pulls its band down and belongs in its improvements.
3. **Read the whole page first, then map it.** Real copy is not labeled by section, sections appear in different orders on different pages, and one passage can do two jobs at once (an opening "lead" often paints the dream AND twists the knife AND carries the subheadline). Map the copy to the sections by FUNCTION, not by looking for labels. A single passage may count toward more than one section; say so. Produce the report in ONE pass and flag any mapping you are unsure about inline (for example: "I read this block as your painting-the-dream, though it may be meant as part of your lead, tell me if so"). Do not stop to ask before scoring.
   - **Don't force a section onto a line that isn't doing that section's job.** The subheadline is the easiest to mis-assign: the line right under the headline is often the first line of the lead or the opening of the dream, not a true subheadline. A real subheadline exists to strengthen the headline and push the reader into the lead by adding something new (proof, specifics, deeper curiosity, or an objection handled). If the line below the headline is really the start of the lead or the dream, do NOT relabel that line as the subheadline; name what it is actually doing. Apply the same test to every section: credit it only where the copy actually does that job.
   - **Story-lead exception for the subheadline and eyebrow.** When the headline deliberately flows straight into an immersive STORY lead, a missing subheadline (and often a missing eyebrow) is frequently the RIGHT call, because forcing one in would break the story's flow. In that case, set the subheadline and eyebrow aside from the score (note they are intentionally skipped for a story lead) rather than counting them as gaps. Only treat an absent one as a gap when adding it would genuinely help. Outside a story lead, an absent subheadline is a real gap, since it is near-universal.
   - **Quote headlines usually mean a story lead.** When the headline itself is a quote (a line in the reader's or a client's own voice) rather than a statement, it usually signals a story or immersive lead. Two consequences: an eyebrow above it does not fit and reads as confusing, and a separate subheadline is often unnecessary too, because the quote flows straight into the lead. So do not treat a missing eyebrow or a missing subheadline as a gap there, do not suggest adding either, and do not map the first line of the lead as a "subheadline." If the reader needs to be identified, the promise sharpened, or a method named, do it inside the headline or the lead itself, not by inventing a subheadline the page does not have.
4. **Judge relevance for every section not clearly present** (the "which sections are actually relevant here" job):
   - Near-universal sections (first part: headline, subheadline, painting the dream, twisting the knife, about you; offer part: offer introduction, guarantee, buy buttons, FAQ, close): if missing, treat it as a real gap unless there's a clear reason it doesn't fit this page. Some reasons to skip one: a story lead can rightly skip the subheadline and eyebrow, warm traffic can make a formal About You optional, and the guarantee follows its own rule in the section-specific handling. Absent such a reason, a missing near-universal section counts against the page score.
   - Situational sections: judge whether the section meaningfully applies to THIS product and audience (follow the product-dependent rule in SKILL.md's standing rules, judge-and-tell; genuinely ambiguous: make the best call and say it in one line; the user can override and the score is recomputed). If it clearly applies and is missing, it's a gap. If it clearly doesn't apply, set it aside (out of scope) with a one-line reason, and it does not count against the score.
   - Watch the natural overlaps and don't double-penalize: counter-mechanism and unique mechanism often travel together; the reframe and the responsibility shift overlap; old-way-new-way can carry the reframe. If one passage does the job of two, credit it and note it rather than marking the twin "missing."
   - **Consider the traffic temperature.** Some sections matter far more for cold traffic than for warm. If the page is written for WARM traffic (an existing email list or audience who already know the author), a formal About You / self-introduction is sometimes optional, and a light or absent one is not necessarily a gap, since the reader already knows and trusts who is speaking (the same can apply to heavy credential-building). Where the copy signals warm traffic (casual references like "my readers", an email-style open, no re-introduction of who the author is), don't auto-penalize a light or missing About You: note the assumption and say plainly that a clear introduction would matter more if this went to cold traffic. Where the traffic is genuinely unclear and it changes the call, give the call for each.
   - **Apply the section-specific handling above** for the guarantee, buy buttons, price justification, product tiers, client journey, guided tour, sample lesson, and urgency and scarcity. Those notes override the default relevance and scoring for those sections (which absences are scored gaps, which are set aside, and which additions can ever be a MUST).
5. **Band every present section** as Strong, Moderate, or Weak (definitions below).
6. **Run the light proof scan and the light flow scan** (the two subsections above). These are quick whole-page reads that feed the report and the priorities, and they do not change the section-based page score. They run where the piece has the length for them; on a short piece they become one line or are skipped, silently.
7. **Compute the page score** (below) and write the report (format below), with the section-by-section part in the order the sections actually appear on the page being audited.

## The bands (judge consistently, the same copy always lands the same way)

Each band has a color marker. Lead every band judgment with its marker (in the section map and in each section heading) so the report is scannable at a glance, the same way the deep audit's scorecard uses status markers.

- **🟢 Strong** — does the section's core job well and hits most of its checklist, with good craft. Few or no meaningful gaps. A reader would be moved by it.
- **🟡 Moderate** — does the core job, but has real, fixable gaps: a key element missing or thin, or craft that sags in places (vague, flat, or off-voice stretches). Solid but leaving conversions on the table.
- **🔴 Weak** — present but not doing its core job. Major elements missing, or craft problems throughout, or "complete but hollow" (the structural parts are there but they don't actually persuade: generic voice, no real proof, no genuine emotion). Say plainly when a section is complete but hollow.
- **❌ Missing (relevant)** — the section is absent and it should be here. Counts as a gap.
- **➖ Set aside (not relevant)** — the section is absent and genuinely doesn't fit this product. Excluded from the score, with a one-line reason.

When torn between two bands, choose the lower one. Don't let "all the parts are present" round a hollow section up to Strong.

## The page score

**The Copy Score is the component score in the engine.** Read `resources/audit.md`'s Scoring section and follow it: The Argument out of 30, Conversion Assets out of 45, Craft out of 25.

**The per-section bands you just produced are the diagnostic layer**, and they feed The Argument component. They are not the headline number.

**Nothing in Conversion Assets can be set aside.** A page with no guarantee scores zero on risk reversal rather than having it excluded.

**Give the one-line meaning**, and give the distribution anchors their due: most pages land 40 to 65, and a score above 70 usually means something was rounded up.

## The report (write it in this order)

Write the whole thing in plain, natural prose in the coach voice, the way a copy coach would talk it through. The reader has never seen the doctrine, so never use internal terms, criterion numbers, or example names; explain every concept in plain words, and describe any illustrating example anonymously and concretely. Because a whole-page report runs long, use bullet points to keep it scannable: bullet the section map, the list of fixes inside each section, the proof and flow findings, the sections worth adding, and the priorities. Keep prose for the overall read and for the sentence or few that explain why each section lands where it does, and put the concrete fixes in bullets. The aim is depth and readability together: rich, specific analysis, laid out in bullets rather than dense paragraphs.

**One idea per paragraph, about 50 words at most** (`coach-voice.md`). The "sentence or few" that explains a band is one short paragraph; anything longer becomes bullets.

**1. Overall read + page score.** Put the score right in this section's heading so it is the first thing seen (for example: "Overall read + page score: 64/100"). Then a short paragraph or two: your honest overall impression of the page and the one biggest lever. Do NOT summarize what the product is or who the audience is; the user wrote the page and already knows, so spending their attention to tell them their own product back gives them no payoff. Go straight to the read they cannot get on their own: what is strong, what is holding the page back, and the single highest-leverage move. Name that lever as a specific, page-specific insight (the one concrete change that would help most, ideally one that fixes several sections at once), rather than a generic "tighten it up," and show it with a concrete example rather than an abstract instruction. Include the score's one-line meaning (what it counts and what it sets aside).

**2. The section map.** Open with one or two sentences of context: this is the reverse-engineered flow of the page, section by section, in reading order, and the color marks how well each section does its job (🟢 green = strong, 🟡 yellow = works but has real, fixable gaps, 🔴 red = present but not doing its job). Then a scannable list, in page order, grouped under the stage of the page each section falls in: **The Opening**, **The Body**, **The Offer**, **The Close** (skip a stage heading if the page has nothing there). One line per section, led by its marker:
- **Green sections:** just name the section. Do not explain why it is green; the obvious ("a thorough FAQ") adds nothing and wastes the reader's attention.
- **Yellow and red sections:** name the section, then state the key improvement(s) in a few words, not a vague description. For example "Buy buttons, no summary of what's included and no proof near the button" or "About you, no proof behind the claims," rather than "Buy buttons, essentials present but the block is bare."
Then a short "what's missing or set aside" list, using ❌ for relevant sections that aren't there (gaps) and ➖ for ones you set aside as not applicable (each with a one-line reason). Flag any uncertain mapping here in plain words.

**3. Section by section: the improvements.** This is the heart of the report, so go deep here; this is where the value is, not the score. Go through the sections in page order, and focus on the ones that need work:
- **Cover the sections that have something to improve.** Skip a Strong section that has nothing worth changing. Include a Strong section only when it has a real (even if minor) lift, and then give just that lift. Spend the most on Yellow and Red sections.
- Lead each section's heading with its color marker and band (for example "### Headline — 🟡 Moderate").
- **Lead with improvements, not praise.** The body is the fixes, one per bullet (a Yellow section with three or five issues gets three or five bullets). Do not spend words on praise or observations that don't lead to a change: a line like "this is the strongest section on the page" doesn't help the user improve anything, so cut it. Mention a strength only when it directly informs a fix. Where a section's job is not common knowledge to a non-expert (a responsibility shift, a reframe, a counter-mechanism), briefly explain in plain words what that section does and why it matters, so the improvement lands and teaches.
- **Be specific, never vague.** For each fix, pull the exact copy that needs work in quotes, then give the specific change. Show the shape of the fix as "turn '[the exact line]' into something like '[a concrete rewrite]'," built from THIS page's own words, scenarios, and audience and written in the piece's own voice (`rewrite.md`, sections 3 and 4), with placeholders for any real fact you don't have (`[a specific number]`, `[a real result]`) rather than inventing one. A vague suggestion ("make it more specific," "name your method in the headline") is not enough on its own; ALWAYS pair a structural suggestion with a concrete worked example.
- **Honest specificity (stay concrete AND honest).** Keep giving concrete example rewrites; they are the most valuable part of the report. When an example leans on a fact only the user has (a real student story, a specific product detail, a true customer scenario, an exact number), present it as clearly illustrative through the WORDING, "something like '[example]', if that matches a real student," rather than as if it were their actual fact. When a fix needs no private context (naming a mechanism, cutting repetition, fixing structure, reordering, removing a hype word), just tell them to make the change. Show this distinction through phrasing only; NEVER label a suggestion "(prescriptive)," "(illustrative)," or "(no context needed)" in the report, those tags are confusing and add nothing.
- **Don't flag missing common visuals.** Assume the visuals almost every page has (an author photo, ordinary section graphics) are present. Do not suggest adding a photo or a generic graphic as an improvement; if you do mention one, frame it conditionally ("if you haven't already added a photo of yourself"). Reserve a visual suggestion for a specific graphic the doctrine calls for and the copy clearly lacks (for example, a mechanism diagram).
- **Don't call a scaffolded-but-empty section "missing."** If the copy sets a section up (heading + lead-in) but its content isn't in the text you were given, assume it's an image or embed you couldn't read, not absent content. This is very likely present on the live page as an image, graphic, or embedded video that simply didn't come through as text (a bonus stack, a testimonial gallery, an expert endorsement, a comparison graphic). Name it in the "couldn't read" line (SKILL.md); never band it 🔴 or list it as a gap (in the section map or in "Sections worth adding"). Only call something a genuine gap when the copy neither contains it nor scaffolds it anywhere on the page.
- **Deeper desire and emotion are a guess, so coach, don't assert.** When a fix depends on the audience's underlying desire or the emotion they are really chasing (the payoff beneath the surface goal), do not state one as fact. Offer it as an example and prompt the user to pin down their audience's real desire, something like: reach past the surface goal to the deeper payoff (belonging, pride, freedom, whatever it truly is for them), and to find it, ask why they care about this in the first place and what they want to feel, experience, or achieve, then tie the dream to that.
- **Naming a mechanism or counter-mechanism: give three options.** When the fix is to name the trap or the fix (a mechanism or counter-mechanism), offer three different name ideas rather than one, so the user has a real choice, and make clear the final name is theirs to pick.
- **Cold vs. warm audience.** When a suggestion depends on how warm the traffic is (whether to add an audience call-out, how much belief-building or proof is needed, how hard to push, how much to re-introduce the author), say so plainly, because you cannot tell which from the page alone. Note that the right move differs for cold traffic (who need more identification, proof, and convincing) versus warm traffic (an existing list who already trust the author and need less), and give the call for each rather than assuming one.
- Still give a real short read to sections that are woven in rather than built out (a reframe line, an old-way/new-way contrast, a responsibility shift): thin and worth building into its own section, or fine as is.
- **Light subheadings check (woven in, not a separate report).** As you go, notice the section's subheading (and the page's headline and any mid-section subheads). If one is particularly off, weak, generic, confusing, or hype-y, call it out right there in that section's analysis and suggest a stronger direction with a concrete example. Only flag the ones that genuinely stand out; do not grade every subheading. (The full subheadings audit lives in `resources/deep-audit.md` for when the user wants all of them.)

**4. Sections worth adding.** For each relevant-but-missing section: name it in plain language, say exactly where in the current copy it should go (between which two existing parts), and give a few sentences on what it should contain and do, with a concrete example where it helps. Order these by where they'd sit on the page. Skip the set-aside ones here (they were already explained in the map).

**5. Proof across the page.** A short read from the light proof scan: whether the page has enough proof overall, whether it is positioned well (a little early, the bulk after the product introduction), and any obviously bold claim left unbacked where the reader would doubt it (pull the exact claim in quotes). A line or two, plus the one or two most useful moves (add proof, move proof earlier or later, back a specific claim on the spot). Say you are going by what the copy shows.

**6. Flow check.** A short read from the light flow scan: if the page reads smoothly, say so in a line; if not, name the two or three most obvious breaks by where they sit (a tangent, an abrupt jump, a missing bridge) and the quick fix for each. Keep it high-level, not section by section.

**7. Priorities: where to spend your time.** Three short lists that pull from everything above (including the proof and flow reads):
- **MUST improve** — the changes that move the page most: weak sections doing an important job badly, and any missing section that genuinely fits this page. Adding a well-fitting section the page lacks is one of the strongest conversion levers there is, so default a missing-but-relevant section to MUST unless it is truly minor or would feel forced in this copy. Exception: the optional second-part sections in the section-specific handling (price justification, sample lesson, guided tour, product tiers) never go in MUST, they belong in NICE or OPTIONAL; and client journey is not suggested at all.
- **NICE to have** — real, non-urgent gains: lifting a moderate section, deepening a section that already works, building a lightly-woven idea (a reframe line, an old-way/new-way contrast) into its own fuller section, tightening craft. These are genuine improvements, not throwaway polish.
- **OPTIONAL** — genuinely minor polish, or situational additions that might not fit this particular page well.
Judge every addition on fit, not on a fixed rank: a section that would slot in naturally and do a real job belongs in MUST; reserve OPTIONAL for what is truly minor or would feel forced here. Keep each item to a line, phrased as an action ("add a twisting-the-knife section after the dream," "make the guarantee specific with a real number"). Where a MUST or NICE item replaces something that already works (a new headline or lead, a changed core promise, a big reorder), say in a few words that it's worth A/B testing against the current version rather than swapping in blind; where a fix is plainly safe, say nothing about risk at all.

**8. The close.** End with the close in SKILL.md under "The close".

## Delivery

The report is delivered in chat, in full. No file is written by default and no folder is resolved; SKILL.md's delivery rule governs. If the user asks for a saved copy, save the report as delivered, `light-audit-YYYY-MM-DD.md` (or `.docx` for Word), name it yourself, and say where it went.

## Rules

- Follow the global plain-language rule in SKILL.md's standing rules: never name internal doctrine terms or examples to the user. Explain concepts in plain words; describe examples anonymously and concretely.
- Follow the product-dependent / relevance rule in SKILL.md's standing rules: judge whether a situational section applies, tell the user your call; genuinely ambiguous: make the best call and say it in one line; the user can override and the score is recomputed. Never set aside a near-universal section without a clear reason.
- Assess and suggest only. Short directional "X into Y" examples are allowed to make a fix concrete. The report never hands back a rewritten page or section; rewrites follow `rewrite.md` when asked, and are offered only in SKILL.md's close.
- Never fabricate human material (numbers, testimonials, stories, mechanisms, results). Use placeholders in any example.
- Base every judgment on the doctrine files or on a guideline in `copy-types.md`, not general opinion. Never invent a critique or improvement: every issue you raise and every fix you suggest must trace to a principle in a doctrine or to a guideline in `copy-types.md`, not to a guess about what "feels" off. If you cannot ground a criticism in the doctrine or in `copy-types.md`, do not raise it (for example, do not tell the user to merge separate FAQ questions, which are legitimate distinct questions, unless the FAQ doctrine actually calls for it).
- Produce ONE report in a single pass. Don't show a provisional version, and don't stall on section-mapping; flag uncertainty inline and keep going.
- Order the section-by-section part by the sections' actual order on the page being audited (it differs page to page), not by the order in this file.
- The page score reflects only in-scope sections. If the user later marks a section not-relevant (or relevant), recompute and show the new number.
